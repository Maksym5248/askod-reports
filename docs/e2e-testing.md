# Desktop E2E-тести

## Рівні перевірок

- **Backend / Vitest** — domain-правила, HTTP-контракти, транзакції, міграції й межі архітектури.
- **E2E / Playwright Test** — справжнє вікно Electron, React, локальний HTTP backend та SQLite.
- **Smoke** — один E2E-сценарій із тегом `@smoke`: запуск, готовність робочого простору,
  відповідь backend і відсутність Node API в renderer.

Великий `scripts/smoke-desktop.ts` замінено незалежними `.spec.ts`.
`npm test` не запускає E2E: вони виключені у `vitest.config.ts` і мають окремий runner.

## Команди з кореня репозиторію

```sh
npm run build                 # потрібна актуальна збірка Electron/backend/renderer
npm run test:desktop          # тільки короткий smoke
npm run test:e2e              # усі 16 E2E-сценаріїв, включно зі smoke
npm run test:e2e -- documents.spec.ts
npm run test:e2e -- --grep "does not overwrite"
npm run test:e2e:report       # HTML-звіт останнього запуску
npm test                     # окремо 29 backend-тестів
```

Потрібна GUI-сесія; тести самі видаляють `ELECTRON_RUN_AS_NODE` з env дочірнього процесу.
Браузери Playwright завантажувати не потрібно: запускається встановлений Electron.
На Linux CI використовується Xvfb та системні бібліотеки для Chromium/Electron.
Скрипти тестів не перебудовують застосунок автоматично; після зміни коду виконайте build.

## Структура

```text

    documents.spec.ts
    deletion.spec.ts
```

Сценарій `layout.spec.ts` перевіряє вікна 960×640 і 1600×1000: таблиця займає
вільний простір, має внутрішню прокрутку, документ сторінки не прокручується,
пагінація залишається видимою. Використовуються 25 синтетичних довгих документів.

## Ізоляція та підготовка даних

Кожен тест отримує окремий тимчасовий userData, SQLite-базу, Electron-процес
і HTTP-клієнт із токеном саме цього запуску. Fixture перевіряє фактичний userData.
База, localStorage та зміни одного тесту не переходять у наступний. Профіль видаляється
у finally, зокрема після помилки тесту; працюючий користувацький застосунок не закривається.

Тести імпорту виконують дію через UI. Для сценаріїв редагування, таблиці та видалення
дані готуються через реальний API імпорту: це скорочує повторювані UI-кроки, зберігаючи
справжню валідацію та запис у SQLite. Прямих записів Prisma/SQL або HTTP-моків тут немає.
Паралельна зміна в тесті конфлікту виконується окремим API-запитом навмисно.
XLSX містять тільки синтетичні дані. Helpers використовують journalColumns для формату fixture.

Один worker обмежує навантаження кількох GUI-процесів. Тести незалежні від порядку й
можуть запускатися окремо. Автоматичних retries немає: нестабільний тест має бути видимим.
Expect-очікування перевіряють стан інтерфейсу без довільних sleep.

## Діагностика

- HTML-звіт: `.data/e2e/report/index.html`.
- При збої: screenshot, renderer-errors JSON та Playwright trace в `.data/e2e/results/`.
- Необроблена помилка JavaScript у renderer також провалює тест.
- Trace запускається вручну для Electron context і зберігається тільки при збої.
- Excel-завантаження перевіряється через Electron `will-download`, автоматично
  зберігається у тимчасовий профіль і повторно читається ExcelJS.

Артефакти містять тільки тестові дані й ігноруються Git. CI зберігає їх після збою.
Тестування проходить проти build у checkout; інсталятори, автооновлення, ОС-діалоги
збереження та різні ОС не вважаються перевіреними цим набором.

## Що перевіряти на якому рівні

Повні комбінації enum, 100+ помилок, rollback, міграції та SQL-унікальність перевіряє
backend suite. E2E перевіряє користувацькі сценарії поверх цих правил. Це не повна
матриця всіх можливих значень і клітинок: нові редактори, фільтри та багатокористувацькі
сценарії мають отримувати власні тести при розвитку застосунку.
